Likely engineering conclusion for Copilot:
The app is probably over-updating its ongoing foreground-service notification while optimization work is running. Android is explicitly rate-shedding notification enqueues for package `com.zfkirke0109.galaxyoptidroid`, notification ID `1001`, on channel `optimization`.

Copilot implementation guidance:

- Search for WorkManager workers, foreground optimization workers, foreground-service notification builders, and `notify(1001, ...)` or equivalent constants.
- Centralize foreground optimization notification updates behind a throttle/debounce layer.
- Do not call `NotificationManager.notify()` for every tiny progress/event tick.
- Only update the notification when user-visible fields actually change.
- For progress, coalesce updates. Prefer at most 1 update/sec unless the operation begins, completes, fails, is cancelled, or changes phase.
- Cache the last published notification state, including title, text, progress max/value, indeterminate state, action set, and importance-sensitive fields.
- Skip publishing when the next notification state equals the last published state.
- Keep the foreground-service notification alive; do not remove the required ongoing foreground notification while work is still active.
- Keep `setForeground()` / `setForegroundAsync()` calls minimal. Use them when entering foreground work or when materially changing foreground info, not for every progress tick.
- Ensure the notification channel `optimization` is created once, not repeatedly in hot paths.
- Add structured debug logging around notification publish decisions:
  - published
  - skipped_duplicate
  - skipped_throttled
  - forced_terminal_update
- Consider a small testable class such as `OptimizationNotificationThrottler`, `ForegroundNotificationState`, or `OptimizationNotificationPublisher`.

Suggested acceptance checks:

- Running one optimization job should not produce Android `NotificationService: Package enqueue rate ... Shedding` errors.
- Foreground-service notification remains visible and compliant during active work.
- Progress still updates smoothly enough for users but not faster than the throttle limit.
- Final completion/cancel/error state is always published immediately, bypassing normal throttling.
- No broad notification behavior changes outside the optimization foreground-service notification path.
